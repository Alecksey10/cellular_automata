# Резервные копии

Бэкап состоит из каталога с тремя файлами:

```text
backups/<идентификатор>/
├── database.dump   # формат PostgreSQL custom, создаётся pg_dump
├── images.tar.gz   # все файлы каталога изображений
└── manifest.json   # метаданные и SHA-256 артефактов
```

`manifest.json` валидируется Pydantic-моделью, содержит версию формата, идентификатор, время создания, сведения о базе, количество и общий размер изображений, а также размеры и SHA-256 файлов бэкапа. Поле `metadata` и дополнительные поля оставлены расширяемыми для будущего анализа. Пароли в метаданные не записываются.

Для создания и восстановления используются штатные клиентские утилиты PostgreSQL `pg_dump` и `pg_restore`, совместимые с версией сервера. Они устанавливаются только в отдельный backup-образ, а не в worker/backend-образ. Python backup CLI также запускается только в отдельном контейнере.

## Команды

При запуске через Compose бэкапы хранятся в `./backups/` в корне проекта и доступны на хосте благодаря volume backend → `/backups`. Внутри контейнера команда запускается из `/app`, но каталог хранения — `/backups`. Успешное создание пишет файлы во временный каталог и затем переименовывает его в каталог снимка, поэтому частично созданный бэкап не попадёт в список.

Из корня проекта сначала соберите отдельный backup-образ:

```bash
docker compose --profile backup build backup
```

Запуск команд выполняется в одноразовом backup-контейнере:

```bash
docker compose --profile backup run --rm backup create
docker compose --profile backup run --rm backup list
docker compose --profile backup run --rm backup verify
```

Для автоматического запуска по расписанию используйте те же команды из cron/systemd timer. Основной `backend`-worker не содержит `pg_dump`, `pg_restore` и backup volume. Если UID пользователя на хосте отличается от 1000, задайте `BACKUP_UID` и `BACKUP_GID` в корневом `.env`, чтобы файлы не создавались с неожиданным владельцем.

После `create` файлы будут доступны локально в `./backups/<backup-id>/`:

```text
backups/<backup-id>/
├── database.dump
├── images.tar.gz
└── manifest.json
```

## Восстановление

```bash
docker compose --profile backup run --rm backup restore 20261016T120000Z_ab12cd34 --replace-database --replace-images
```

`--replace-database` обязателен: `pg_restore --clean --if-exists` удаляет объекты целевой БД, которые есть в дампе, и восстанавливает их. Для полного восстановления каталог изображений тоже заменяется при `--replace-images`. Перед этим система проверяет метаданные, размеры, контрольные суммы и содержимое архива изображений.

Чтобы восстановить только картинки:

```bash
docker compose --profile backup run --rm backup restore 20261016T120000Z_ab12cd34 --images-only --replace-images
```

## Ограничения текущей версии

- Бэкап создаётся для одной базы и одного каталога изображений, заданных окружением.
- Снимок БД формируется `pg_dump`; каталог картинок архивируется непосредственно из файловой системы. Если приложение активно меняет картинки во время операции, снимок файлов не является синхронной транзакцией с БД.
- Проверка целостности офлайн сверяет сохранённые размеры и SHA-256. Она не подтверждает, что дамп успешно импортируется в конкретную версию PostgreSQL.
