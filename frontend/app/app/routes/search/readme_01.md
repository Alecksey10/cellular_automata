# 1

Да. Если собрать всё, что мы сегодня проектировали, то твоя идея на самом деле не столько про «поисковую строку», сколько про изолированную машину поиска с самостоятельным жизненным циклом, которую UI только подключает и отображает.

Ниже я бы зафиксировал требования именно слоями — от архитектурной концепции к конкретному API.
1. Самый абстрактный уровень

Система поиска должна быть отдельной подсистемой страницы.

Есть три основные стороны:

Пользователь
    │
    ▼
Страница / UI
    │
    ▼
Машина поиска

Пользователь

Пользователь взаимодействует с интерфейсом:

    вводит текст;
    выбирает предложения;
    нажимает Enter;
    нажимает Escape;
    переводит фокус;
    изменяет поисковую строку.

Пользователь не взаимодействует непосредственно с внутренними механизмами поиска.
Страница

Страница является владельцем поискового окружения.

Она:

    создаёт и инициализирует машину поиска;
    передаёт ей необходимые зависимости;
    подключает UI-компонент;
    получает события от поискового компонента;
    при необходимости реагирует на применение поиска;
    загружает основной контент страницы.

При этом страница не должна знать внутреннюю реализацию поиска.

Например, ей не нужно самостоятельно:

разбирать tag:game
проверять существование tag
формировать autocomplete
валидировать DSL

Машина поиска

Машина поиска — самостоятельное окружение, ответственное за организацию поиска.

Она должна уметь:

    хранить текущее состояние поиска;
    разбирать поисковую строку;
    валидировать её;
    дополнять ввод;
    работать с внешними справочными данными;
    преобразовывать строку в структурированный запрос;
    уведомлять UI об изменениях;
    принимать команды от UI.

Главный принцип:

    Поисковая логика не должна принадлежать странице и не должна принадлежать React-компоненту строки.

2. Следующий уровень — поисковая подсистема

Машина поиска представляет собой не один большой класс, а окружение из специализированных сущностей.

Концептуально:

Search Environment
│
├── Parser
├── Validator
├── Completion
├── Data Provider
├── Query Builder
└── Input State / Events

Каждая сущность отвечает за свою концепцию.
3. Parser — понимание языка поиска

Parser отвечает только за то, чтобы понять:

    «Что пользователь написал?»

Например:

game tag:physics owner:me sort:popular

превращается в промежуточное представление:

text:
    game

tags:
    physics

owner:
    me

sort:
    popular

Parser не должен заниматься UI.

И не должен знать, как React отображает ошибку.

Его задача — распознать язык.
4. Validator — проверка корректности

Validator отвечает за вопрос:

    «Является ли разобранное выражение допустимым поисковым запросом?»

В частности, система должна различать:

empty
incomplete
valid
invalid

Например:

tag:

это не обязательно синтаксическая ошибка.

Это:

incomplete

А:

taa:12

— ошибка, потому что taa не является поддерживаемым оператором.

Это было одним из важных требований, которое выявилось при тестировании:

    Неизвестные конструкции нельзя молча интерпретировать как обычный текст.

5. Completion — механизм дополнения

Completion отвечает на вопрос:

    «Что пользователь, вероятно, хочет написать дальше?»

Например:

tag:g

может предложить:

tag:game
tag:game-of-life

А после пробела:

tag:game |

предложения уже относятся к новому выражению, например:

tag:
collection:
owner:me
sort:

То есть completion должна понимать позицию пользователя в языке поиска, а не просто искать совпадения по последнему слову.
6. Data Provider — доступ к дополнительным данным

Autocomplete не должен содержать сами теги и подборки.

Он должен обращаться к абстракции:

SearchDataProvider

которая предоставляет:

searchTags()
searchCollections()
getTagByName()
getCollectionByName()

Сейчас это mock.

Позже:

MockSearchDataProvider
        ↓
API SearchDataProvider
        ↓
сервер

Это важно для твоего первоначального требования:

    теги и подборки могут догружаться со временем.

Следовательно, поисковая машина не владеет источником данных.

Она зависит от абстракции получения данных.
7. Актуализация данных

Из этого следует следующий архитектурный принцип.

В будущем между машиной поиска и API может появиться кэш/прокси:

SearchCompletion
       │
       ▼
SearchDataProvider
       │
       ▼
SearchDataCache
       │
       ▼
API

Например:

первый запрос:
tag:gam
       ↓
API

последующие:
tag:gam
       ↓
cache

При этом Completion ничего не знает о том, откуда данные взялись.

Это соответствует твоей первоначальной идее:

    отдельная прослойка для хранения, получения и актуализации необходимых данных.

8. Query Builder — перевод во внешний запрос

После того как строка разобрана и проверена, появляется отдельная задача:

    «Как представить поиск в форме, понятной серверу?»

Например:

tag:game owner:me sort:popular

становится:

SearchQuery

{
    tags: [...],
    owner: "me",
    sort: "popular"
}

А уже потом эта структура может превратиться, например, в:

?tag=game&owner=me&sort=popular

или в POST:

{
    "tags": ["game"],
    "owner": "me",
    "sort": "popular"
}

Таким образом:

строка поиска
      ↓
Parser
      ↓
ParsedQuery
      ↓
Validator
      ↓
QueryBuilder
      ↓
SearchQuery
      ↓
API

9. Search Environment — координатор

На этом уровне появляется SearchEnvironment.

Его задача — не реализовывать все механизмы самому, а соединять их.

Условно:

                 ┌────────────┐
                 │   Parser   │
                 └─────┬──────┘
                       │
                       ▼
Input ──────────► Environment
                       │
            ┌──────────┼──────────┐
            ▼          ▼          ▼
       Validator   Completion   Builder
                       │
                       ▼
                  DataProvider

Environment знает:

    когда вызвать parser;
    когда validator;
    когда completion;
    когда обратиться к данным;
    когда обновить состояние;
    когда сообщить UI об изменении.

Но отдельные компоненты не знают друг о друге без необходимости.
10. Отдельно — состояние строки

Важная концепция, которая появилась в процессе разработки:

состояние поисковой строки не равно поисковому запросу.

Например, строка может содержать:

tag:gam

при этом:

SearchInputState

может содержать:

value:
    tag:gam

suggestions:
    tag:game
    tag:game-of-life

focused:
    true

suggestionsVisible:
    true

validation:
    incomplete

Это UI-состояние.

А после Enter появляется уже:

SearchQuery

Это состояние применённого поиска.

Их важно не смешивать.
11. SearchInput — отдельный UI-компонент

Именно здесь появилась одна из наиболее важных твоих требований.

Ты не хотел:

Page
└── огромный JSX
    └── вся логика SearchEngine

Ты хотел:

Page
│
├── SearchEnvironment
│
└── <SearchInput engine={...} />

То есть SearchInput — самостоятельный компонент.

Он знает только:

    как отображать строку;
    как отображать предложения;
    как показать validation;
    как передавать действия пользователя движку.

Он не знает, как реализованы:

parser
validator
completion
data provider
query builder

12. Но SearchInput не должен быть захардкожен под конкретный Engine

Это тоже важное требование.

Нежелательно:

<SearchInput />

внутри которого:

new SearchParser()
new SearchValidator()
new SearchCompletion()

Вместо этого:

<SearchInput
    engine={searchEngine}
/>

Компонент получает абстрактный контракт:

SearchInputEngine

Таким образом, теоретически один и тот же компонент можно использовать с:

ProductionSearchEnvironment
MockSearchEnvironment
TestSearchEnvironment

13. API SearchInput разделяется на два направления

Получилась очень чистая граница.
UI → Engine

Компонент сообщает движку:

setInput()
focusInput()
blurInput()
handleEscape()
selectSuggestion()
submit()

Это команды.
Engine → UI

Компонент подписывается на состояние:

subscribeInput()

и получает:

value
suggestions
suggestionsVisible
focused
validation

Это состояние.
14. UI → Page

И отдельно сам React-компонент предоставляет странице события:

onChange
onValidationChange
onSubmit
onFocus
onBlur
onEscape

Это уже не внутреннее API поискового движка, а API UI-компонента.

Поэтому получается три разных уровня интерфейсов:

                 PAGE
                  ▲
                  │ callbacks
                  │
             SearchInput
                  │
                  │ commands/state
                  ▼
          SearchInputEngine
                  │
                  ▼
        Search Environment

Это очень важное разделение.
15. Что означает onSubmit

onSubmit — не просто «нажали Enter».

Семантически:

    Пользователь применил валидный поисковый запрос.

Поэтому:

Enter
  ↓
engine.submit()
  ↓
parse
  ↓
validate
  ↓
build SearchQuery
  ↓
success
  ↓
onSubmit(query)

А если:

taa:12

то:

Enter
  ↓
invalid
  ↓
onValidationChange(...)
  ↓
onSubmit НЕ вызывается

Это позволяет странице очень просто работать:

onSubmit={query => {
    loadAutomata(query);
}}

И странице вообще не надо проверять запрос.
16. Escape и focus

Поведение UI также стало частью отдельного контракта.

При:

Escape

машина должна убрать активные предложения:

suggestionsVisible = false

При:

blur

предложения также исчезают.

При этом это не изменение поискового запроса.

То есть:

Escape

не должен:

очищать value

и не должен:

сбрасывать validation

если это специально не предусмотрено.

Он изменяет именно UI-состояние.
17. Полный жизненный цикл ввода

В итоге архитектура описывает примерно такой процесс:

Пользователь вводит текст
        │
        ▼
   SearchInput
        │
        ▼
 engine.setInput()
        │
        ▼
      Parser
        │
        ├── syntax error ──► invalid
        │
        ▼
    Validator
        │
        ├── incomplete
        │
        └── valid
        │
        ▼
    Completion
        │
        ▼
 Data Provider
        │
        ▼
  Input State
        │
        ▼
    SearchInput

А применение:

Enter
  │
  ▼
engine.submit()
  │
  ▼
Parser
  │
  ▼
Validator
  │
  ▼
QueryBuilder
  │
  ▼
SearchQuery
  │
  ▼
onSubmit(query)
  │
  ▼
Page
  │
  ▼
API поиска

19. Главная концепция, которую ты фактически проектировал

Если сформулировать всю задумку одним предложением:

    Поисковая строка является только визуальным интерфейсом к независимой машине поиска, которая инкапсулирует язык поиска, его состояние, дополнение, валидацию, работу со справочными данными и преобразование в структурированный запрос, не привязываясь к React и конкретной странице.

А ещё короче:

UI ≠ Search Engine ≠ Search API

У каждого свой уровень ответственности:

UI
↓
управление взаимодействием

Search Engine
↓
понимание и организация поиска

Search API
↓
получение результатов

И именно поэтому архитектура хорошо масштабируется, когда завтра вместо трёх операторов появится двадцать:

tag:
collection:
owner:
sort:
size:
views:
author:
language:
rule:
dimension:
created:
updated:

При этом React-страница и SearchInput не должны существенно измениться. Новая функциональность должна в основном появляться внутри поискового окружения — в parser/completion/validator/data/query-слоях
